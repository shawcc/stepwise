# PRD：WorkGraph 最小工作闭环

## 1. 文档状态

- 版本：v0.3
- 日期：2026-08-18
- 状态：原型验证
- 核心概念：[CORE_CONCEPTS.md](CORE_CONCEPTS.md)
- 旧版需求：[archive/PRD.v0.2-legacy.md](archive/PRD.v0.2-legacy.md)

## 2. 产品目标

验证用户能否直接在 WorkGraph 中围绕一个共同目标与 Agent 工作，而不依赖外部聊天窗口。

唯一主流程：

```text
工作图谱
-> 进入 Objective
-> 在目标工作台查看当前结果
-> 从章节或结论打开过程推演
-> 人与 Agent 形成修改提案
-> 人工确认
-> 回写目标文档并生成版本
```

## 3. 非目标

- 不在本期实现完整项目管理系统。
- 不把 IM、通知或普通聊天做成工作主入口。
- 不同时展示所有实验视图。
- 不让 Agent 绕过确认直接改写正式结果。
- 不用模型不可验证的内部思维链冒充推理证据。
- 不承诺生产级权限、多人协同、持久化和 Agent 调度。

## 4. 核心对象

| 对象 | 定义 | 是否递归 |
|---|---|---|
| Objective | 希望发生的变化，目标工作的容器 | 是 |
| Key Result | 判断 Objective 是否达成的结果标准 | 否 |
| Necessary Condition | Objective 成立不可缺少的待验证条件 | 否 |
| Initiative | 为创造条件而组织的一组工作 | 否 |
| Action | 可直接执行的最小工作单元 | 否 |
| Outcome | Action 或 Initiative 实际产生的结果 | 否 |
| Evidence | 支持或反驳结果与判断的事实 | 否 |
| Decision | Review 后形成的正式判断 | 否 |

下级 Objective 不是新类型，而是 Objective 的递归关系。需要独立负责人、自己的 KR 或继续拆解时，必要条件或举措应转化为下级 Objective。

## 5. 信息架构

### 5.1 一级入口

原型只突出两个入口：

1. 工作图谱：组织级导航，用于发现目标和理解层级。
2. 目标工作台：具体工作的主入口，用于查看结果、进入过程和回写版本。

### 5.2 派生入口

依赖、证据、监控和时间线保留实现，但收进“更多视图”或暂时隐藏。它们读取同一份工作事实，不形成新数据源。

关注、决策待办、知识库属于未来的注意力和检索入口，不进入当前核心导航。

### 5.3 三类信息

```text
当前结果：目标工作台
形成过程：过程推演
变化历史：版本记录
```

三者必须互相可达，但不能混在同一信息层级。

## 6. 页面需求

### 6.1 工作图谱

目的：让用户看见权限范围内的目标整体，并进入任一层工作。

必须：

- 展示当前地图根节点和直接下级 Objective。
- 支持逐层进入下级地图。
- 支持返回上级。
- 支持明确进入当前 Objective 的目标工作台。
- 地图下钻时保持地图模式，不自动切换工作台。
- 无权限目标不展示敏感内容。

暂不突出：

- 全类型事实节点。
- 复杂关系筛选。
- 多种观察视图切换。
- 大段产品说明。

### 6.2 目标工作台

目的：在一篇递归目标文档中完成具体工作。

文档结构：

```text
Objective
├── Key Results
├── Necessary Conditions
│   ├── Child Objective
│   └── Initiative
│       └── Action
│           └── Outcome
└── Evidence
    └── Review
        └── Decision
```

必须：

- 展示 Objective 的标题、负责人和当前状态。
- 依次展示目标与 KR、必要条件、路线、执行结果、审查决策。
- 下级 Objective 作为内嵌文档入口，可以继续递归。
- 每个章节和关键结论提供“过程推演”入口。
- 有过程时允许在正文折叠预览最近记录。
- 切换 Objective 后默认回到第一章节。
- 正文只显示已确认结果，不直接混入草稿和讨论。

收敛：

- 隐藏与正文必要条件重复的“直接下级”快捷条。
- Plain-text 结构摘要默认折叠。
- 隐藏无助于当前工作的解释性文案。
- 保留左侧文档目录，但不增加第二套流程导航。

### 6.3 过程推演

目的：承载人和 Agent 围绕某个章节或结论的共同工作。

打开方式：

- 点击章节的“过程推演”。
- 悬停或聚焦具体结论后点击“过程推演”。
- 从正文中的过程预览打开完整面板。

必须展示：

- 当前 Objective、章节和锚定结论。
- 当前正式结果或待编辑草稿。
- 历史事件：用户输入、AI 分析、提案、决策和系统记录。
- 推演总结：轮次、AI 分析数、提案数、正式版本数。
- 首版与最新版之间的结论变化摘要。
- 当前阶段可用的专业方法及检查项。

必须操作：

- 用户输入修改要求。
- Agent 读取当前 Objective、上下游、阶段、方法和草稿。
- Agent 返回结构化提案、理由和待确认问题。
- 用户采用提案进入草稿。
- 用户编辑草稿。
- 用户确认并写入正式结果。
- 系统生成版本和 Decision 事件。
- 用户可以发起 Redo；生产版本需计算影响范围。

约束：

- Agent 输出默认是提案。
- 未确认内容不得覆盖正式文档。
- 展示的是可审查依据、提案和决策，不声称展示模型内部思维链。

### 6.4 版本记录

必须：

- 记录 Objective、章节、正文、确认人和确认时间。
- 同一 Objective 的不同章节分别版本化。
- 保留历史版本，不覆盖。
- 能从版本回到对应过程推演。
- 能说明结论是否发生实质变化。

当前原型允许使用浏览器本地存储；界面必须明确其非生产属性。

## 7. Agent 协作协议

请求上下文至少包含：

```yaml
objective:
  id: string
  title: string
  owner: string
  parent: Objective | null
  children: Objective[]
stage: objective | conditions | route | execution | review
method: string
confirmed_result: string
current_draft: string
user_request: string
```

返回结果：

```yaml
proposedDraft: string
rationale: string
questions: string[]
provider: string
```

前端不得把 `proposedDraft` 直接写入正式结果。只有用户确认后，才能写入并生成版本。

## 8. 状态模型

### 草稿状态

- `clean`：草稿与正式结果一致。
- `editing`：用户或 Agent 已修改，尚未确认。
- `proposed`：存在可采用的 Agent 提案。
- `confirmed`：已写入正式结果并生成版本。
- `error`：Agent 请求失败，保留现有草稿。

### 线程事件

- `comment`：人类输入或问题。
- `agent-analysis`：Agent 提供的可审查分析摘要。
- `proposal`：建议写入的结构化草稿。
- `decision`：确认、拒绝、调整或重做。
- `system`：版本生成、执行结果等系统事件。

## 9. 数据与治理

所有正式工作事实最终需要包含：

- 责任主体。
- 来源。
- 权限。
- 时间。
- 版本。
- 状态。

生产实现还需要：

- 服务端数据库。
- 用户身份和组织权限。
- 多人并发与冲突处理。
- Objective、Evidence、Decision 和 Version API。
- Agent 工具权限和审计。
- Redo 影响传播。

## 10. 验收标准

### 核心闭环

1. 用户从工作图谱逐层进入一个 Objective，视图不会意外切换。
2. 用户进入目标工作台后，能识别当前结果和五个文档章节。
3. 用户能从任一章节或关键结论打开正确锚点的过程推演。
4. 用户提交要求后，Agent 返回提案但不直接修改正式结果。
5. 用户采用并编辑草稿后，可以确认写入。
6. 确认后生成新版本和 Decision 事件。
7. 重新打开该过程时，可以看到历史事件、统计和版本变化。
8. 用户进入下级 Objective 后，从第一章节开始工作。

### 信息收敛

1. 一级工作入口只突出工作图谱和目标工作台。
2. 依赖、证据、监控和时间线不与主入口并列争夺注意力。
3. 目标工作台不重复展示直接下级快捷条。
4. Plain-text 结构摘要默认不占据正文空间。
5. 页面没有用于解释产品本身的大段可见文案。

### 技术检查

```bash
npm run lint
npm run check
npm run build
```

## 11. 后续优先级

1. 用真实工作完成多轮“提案 → 确认 → 版本”闭环。
2. 将 Objective 和过程事件迁移到服务端。
3. 增加身份、权限和多人协作。
4. 实现真实 Evidence 上传、核验和 Review。
5. 实现 Redo 影响传播。
6. 根据真实使用恢复必要的派生观察视图。
