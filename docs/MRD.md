# MRD：WorkGraph

## 1. 产品定义

WorkGraph 是面向 Agent 原生组织的共同目标工作系统。

组织通过工作图谱找到共同目标，在目标工作台中工作，通过过程推演完成人与 Agent 协作，并将确认结果回写为可追溯的组织事实。

```text
注意力入口：通知 / IM / 待办
组织导航：工作图谱
具体工作：目标工作台
共同过程：过程推演
正式结果：目标文档与版本
```

核心概念以 [CORE_CONCEPTS.md](CORE_CONCEPTS.md) 为准。

## 2. 立项判断

当前主流产品仍以“每个人配一个 Agent 助理”为中心。WorkGraph 验证一个更长期的判断：未来组织可能由少量人治理大量 Agent，人类主要负责目标、授权、价值判断和高风险决策，Agent 负责读取上下游、提出方案、执行和检查。

当 Agent 数量和工作密度上升，聊天、文档和任务列表会暴露三个问题：

- 目标、判断、行动和证据分散，Agent 无法稳定共享上下文。
- 讨论过程与正式结果混杂，无法判断什么已经确认。
- 下游失败难以回流到上游目标和原始判断。

WorkGraph 的机会不是制造一个更会聊天的 AI，而是建立人和 Agent 共同工作的事实层与控制回路。

这仍是产品假设，需要通过真实工作验证，不作为已被市场证明的事实。

## 3. 目标用户

### 核心用户

- 组织负责人：定义方向、关键结果和治理边界。
- 目标负责人：承接目标，组织下级目标、举措和行动。
- 人类专家：处理价值判断、例外和高风险决策。
- 专项 Agent：读取目标上下文，分析、提案、执行、补证和互审。

### 首个验证场景

跨职能、持续数周以上、需要多次判断和调整的共同目标，例如“构建未来的工作平台”。

这类工作同时需要：

- 看见整体目标与递归层级。
- 解释每项工作为什么存在。
- 保留人和 Agent 共同形成结论的过程。
- 用证据检验结果并在必要时重做。

## 4. 用户问题

- 我应该从哪里进入一项共同工作？
- 当前确认的目标和结论是什么？
- 这个结论基于什么信息、经历了哪些提案和决策？
- 某个下级目标为什么存在，服务哪个上级目标？
- Agent 能做什么，哪些修改需要我确认？
- 行动完成后，证据是否真的支持关键结果？
- 判断错误时，应从哪里重做，哪些下游会受影响？

## 5. 产品主张

### 5.1 Objective 是唯一递归目标单元

目标不再分成 Goal、SubGoal 和 Work Unit 三套对象。需要独立负责、拥有自己的关键结果并继续拆解的工作，统一成为下级 Objective。

### 5.2 OKR 是入口，推理与证据是内核

- Key Results 回答“怎样算成功”。
- Necessary Conditions 回答“成功依赖什么”。
- Initiative 组织一组工作创造条件。
- Action 负责直接执行。
- Outcome 与 Evidence 说明实际发生了什么。
- Review 用证据形成 Decision。

### 5.3 目标工作台是具体工作的主入口

目标工作台是一篇递归目标文档，只呈现当前已确认的结果。用户不需要先理解底层图谱对象，便可以围绕一个目标开始工作。

### 5.4 过程推演承载共同工作

每个关键结论都能打开其过程推演。过程推演保存问题、讨论、AI 分析、修改提案、审查和决策，不把未经确认的内容直接写入正式文档。

### 5.5 Agent 提议，人类按风险治理

默认闭环是：

```text
Agent 读取上下文
-> 提出结构化修改
-> 人类审查
-> 确认写入
-> 生成版本
```

未来可按权限、风险、可逆性和证据充分度允许 Agent 自动推进，但高风险和不可逆事项必须由人处理。

## 6. 产品边界

### 本期验证

- 从工作图谱进入任意 Objective。
- 在目标工作台查看递归目标文档。
- 在章节或具体结论上打开过程推演。
- 让 Agent 基于当前 Objective、上下游和专业方法提出修改。
- 预览提案，人工确认后写入并生成版本。
- 查看历史过程、推演统计和结论变化。

### 本期降低可见性

以下能力保留设计或代码，但不作为一级入口：

- 依赖视图。
- 证据总览。
- 运行监控。
- 全局时间线。
- 关注、知识库和复杂决策中心。
- 通用材料解析和多 Agent 自动编排。

它们只有在核心工作闭环成立后，才按真实需求逐步恢复。

### 当前不承诺

- 生产级数据库、身份、权限和多人并发。
- 自动执行真实业务系统。
- 可靠的通用自然语言逻辑抽取。
- 生产级多 Agent 调度和影响传播。
- 无人工确认的正式结果改写。

## 7. 成功判断

原型阶段不编造增长或效率百分比，先观察以下事实：

- 用户能否在首屏说清当前共同目标和下一步入口。
- 用户能否从地图进入目标并持续向下递归。
- 用户能否区分当前结果、形成过程和历史版本。
- Agent 提案是否被采用、修改或拒绝，以及原因。
- 任一正式结论是否能追溯到过程和确认记录。
- 行动、结果和证据是否仍能追溯到所属 Objective。
- 用户是否需要被隐藏的派生视图；若需要，具体为解决什么问题。

## 8. 核心风险

- 图谱抽象过度暴露，产品像建模工具而不是工作工具。
- 过程记录退化为聊天流水，不能解释结论变化。
- 文档与图谱被错误理解为两个事实源。
- Agent 生成内容缺少来源、证据或确认门。
- 目标、条件、举措和行动边界不清，再次产生概念重复。
- 功能同时铺开，核心闭环尚未成立就被复杂导航掩盖。

## 9. 产品原则

1. 先让用户围绕共同目标完成工作，再增加观察和治理能力。
2. 工作图谱负责找到目标，目标工作台负责做事。
3. 目标文档保存当前结果，过程推演保存共同工作，版本保存已确认变化。
4. Objective 是唯一递归目标单元。
5. Agent 默认提交提案，不直接改写正式结果。
6. 行动完成不等于目标达成，必须由证据核验关键结果。
7. IM、通知和待办只路由注意力，不承载正式工作事实。
